# 로또 통합 전산 1단계 — 사이트별 조회와 이관 사전 점검

## 적용 상태

- PlusLotto Supabase 적용 및 운영 읽기 검증 완료. 적용 전후 회원 58,031명, 결제 1,614건, 결제 합계 798,657,002원으로 같았으며, 레거시 출처 회원 0명과 추천 발송 보류 60명도 같았다.
- 로컬 화면에서 사이트 전환, 회원·결제·매출·통계, URL 복원, 선택 행 초기화, 신규 회원·결제 출처 저장을 가상 데이터로 확인했다. 실제 고객 등록·결제·문자 발송은 하지 않았다.
- 로컬 브랜치 `codex/site-scope-preflight`에 저장했다. 로컬 Git 인증 부재 및 GitHub 앱의 코드 쓰기 403으로 푸시·PR·머지·Vercel 화면 배포는 미완료다. GitHub 쓰기 연결 복구 후 PR 검사를 통과시켜 기존 Git 배포로 반영한다.

## 이번 변경

- 상단 `관리 사이트`에서 플러스로또·815로또·인포로또·일행로또·전체 사이트를 선택한다. 처음 진입하면 플러스로또를 선택한다.
- 회원, 나의고객, 나의 문자내역, 결제, 대시보드, 매출·캘린더·일일요약, 통계·상담통계에 같은 사이트 범위를 적용한다. 새로고침·뒤로가기·공유 URL에도 `?site=`로 선택을 전달한다.
- 사이트를 바꾸면 선택 행과 열린 회원·결제 상세를 닫는다. 사이트별 조회 캐시를 분리하고 로그아웃 시 이전 계정 캐시를 비운다.
- 기존 `members.meta.source_site`가 없거나 비어 있으면 플러스로또다. 알 수 없는 출처는 전체 사이트에서만 볼 수 있다. 기존 회원 행을 일괄 수정하지 않는다.
- 결제 집계는 연결 회원의 출처를 따른다. 수기로 새로 만든 결제도 같은 회원의 사이트에 귀속된다. 신규 회원 등록·일괄 등록에는 선택한 사이트를 기록한다. `전체 사이트`에서는 등록 대상 사이트를 먼저 선택해야 한다.
- 일일 매출은 DB에서 전체 기간을 집계한다. 회사 전체 근무인원과 1인당 매출은 `전체 사이트`에서만 표시·입력한다.
- 사이트 선택은 조회 필터다. 기존 역할·담당자 RLS에 추가되며, 사이트별 직원 접근 권한을 새로 부여하거나 제한하는 기능은 아니다.
- 관리자·설정·상품·문자 템플릿·문의·로그·베팅·급여 등 나머지 화면은 공통 관리다. 상단에 `공통 관리`를 표시하고 사이트 선택을 비활성화한다.

## 실제 이관 전 필요한 작업

이번 릴리스는 고객 원본 적재나 문자 발송 재개를 수행하지 않는다. 2026-09-09 적용 전 읽기 점검에서 PlusLotto DB의 기존 레거시 출처 회원은 0명이었다. 기존 전산에서 진행 중인 작업으로 일반 회원 수는 계속 변할 수 있다.

1. **815 전체 원본 확보 및 dry-run 재검증.** 기존 기록의 회원 21,809명·결제 28,072건은 8/31 원본 수치다. 신규 검증은 누락·잘못된 조합 수, 상태, 결제수단, 금액을 사유별로 제외하므로 예전 결과를 그대로 승인 기준으로 사용하지 않는다.
2. **충돌·누락 명세 확정.** 전화번호 충돌을 건너뛰는 기존 정책을 유지했다. 같은 전화번호의 다른 사이트 계약과 결제를 어떤 회원에 연결할지 정하고 누락되는 결제까지 대조해야 한다.
3. **브랜드별 문자 경로 분리.** 현재 발신번호·템플릿·가입환영 문자 설정은 공통이다. 타 사이트 회원의 실제 결제 승인·문자 운영을 시작하기 전에 경로를 분리해야 한다. `reco_paused`는 조합 발급·추천문자 보류이며 모든 종류의 문자를 차단하는 스위치는 아니다.
4. **100명 시범 적재 → 화면·결제·담당 대조 → 전체 적재.** 실행 배치 ID를 명시하고 적재 전후 건수·합계·제외 사유를 보관한다. 발송 보류는 대조 완료 후 별도 처리한다.
5. **상담원 대응, 과거 상담·문자·당첨 이력, 전환 시점 이후 변경분 처리.** 현재 로더는 회원·결제 중심이며 이 모든 이력을 완전 이관하지 않는다.
6. **인포·일행 순차 진행.** 기존 수령본이 전체 과거 유료회원을 포함하는지 먼저 확인한다. 프리미엄은 원본·대응표가 준비된 후 추가한다. 88로또는 별도 인프라와 운영 데이터를 유지한다.

원본 경로를 실제로 확인한 뒤 아래 읽기 전용 점검을 실행한다. 파일 경로는 예시가 아니라 실제 확보한 경로를 넣는다.

```bash
cd /Users/seungsoohan/Projects/PlusLotto
bash scripts/preflight-legacy-load.sh lotto815 /실제/815전체원본.zip
```

점검이 통과하면 정확한 `--dry-run` 명령을 출력한다. 이 단계에서 `--apply`를 실행하지 않는다. 사전 점검은 로더와 동일한 원본 파일명·개수·경로 규칙과 ZIP CRC를 검사하며, Supabase에 접속하지 않는다.

## 검증과 배포

- TypeScript 회귀 14개, Python 로더 19개, ZIP 사전 점검 7개, 가상 PostgreSQL 10개.
- PostgreSQL 검증에는 기존 전체 응답 보존, 사이트별 집계, 1,000건 초과 결제, 한국 시간 인식일, 역할/RLS, 기본 인자 호환, 원복을 포함한다.
- 운영 DB 마이그레이션: `supabase/migrations/20260909001521_admin_site_scope.sql`. 새 `daily_work_count` 테이블은 기존에 누락되어 있어 빈 상태로 생성한다.
- 운영 읽기 검증: `scripts/sql/verify-admin-site-scope.sql`. 원복: `scripts/sql/admin-site-scope.rollback.sql`와 프론트 릴리스를 함께 되돌린다. 원복 시 Supabase 마이그레이션 이력도 맞춘다.
- 실제 Supabase에서 생성한 스키마 타입은 `src/types/supabase.generated.ts`다. 기존 도메인 타입 파일 전체 교체는 이번 범위에 포함하지 않는다.
- GitHub `Admin validation`은 PR·main push마다 타입·빌드·로더·DB 검사를 실행한다. Vercel은 기존 Git 연동으로 배포한다. 이 워크플로 추가만으로 GitHub 보호 규칙이나 Vercel 배포 대기 설정이 생기지는 않는다.

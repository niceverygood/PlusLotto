## 5. 검수 대조표 만드는 법

`scripts/make-review-sheet.py` 가 운영 DB를 **읽기만 해서** 사이트별 CSV를 만든다. 쓰기는 구조적으로
막혀 있다(읽기 전용 클라이언트라 GET 이외는 예외).

```bash
export VITE_SUPABASE_URL=...            # 키는 환경변수로만 — 명령행·로그에 남기지 않는다
export SUPABASE_SERVICE_ROLE_KEY=...
python3 scripts/make-review-sheet.py --limit 50 --out /tmp/표본   # ① 표본으로 형태 확인
python3 scripts/make-review-sheet.py --out ./검수대조표_20260928  # ② 전체 생성
```

생성물:

| 파일 | 내용 | 현장이 보는 법 |
|---|---|---|
| `요약.csv` | 사이트별 회원수·등급·발송요일·결제·담당배정 + 전역 스위치 3종 | 구전산 숫자와 한 줄씩 맞춰본다 |
| `<사이트>/발송예정.csv` | 검수 보류 해제 시 문자가 나갈 회원 전체 | 이 명단이 곧 10/5 주간에 벌어질 일이다 |
| `<사이트>/발송제외.csv` | 나가지 않는 회원 + 사유 | "나가야 하는데 왜 빠졌지"를 여기서 찾는다 |
| `<사이트>/점검필요.csv` | 전환 전 손볼 것만 추림 | 연락처 없음·종료일 문제·요일 미지정·담당 미배정 |

**표가 "지금"이 아니라 "보류를 풀면"을 보여주는 이유**: 이관 회원은 전원 검수 보류가 걸려 있어
(`meta.reco_pause_reason='legacy_import_review'`) 현재 상태로 판정하면 전원 "일시정지"로 나온다.
그래서 그 보류만 해제됐다고 가정해 판정한다. 운영자가 따로 건 일시정지는 그대로 제외로 센다.

⚠️ **판정 규칙이 세 곳에 있다** — `api/weekly-reco.ts`(크론) · `src/lib/recoEligibility.ts`(화면) ·

## 6. 마지노선이 10/12 자정으로 확정되며 달라진 것 (9/24)

현장: "10월 13일까지라고 저희 대표님께서 말씀해 주셨으니, **12일 자정까지로 예상하고** 작업해 주심이

하루 차이지만 계산이 바뀐다. 이전 계획은 10/13(화) 발송을 보고 나서 정리하는 것이었는데, 그날에는
구전산이 이미 없다. **검증이 끝나야 하는 마지막 날이 10/12(월)이다.**

| 사이트 | 신전산 발송 시작 | 10/12 자정까지 검증되는 요일 | 판정 |
|---|---|---|---|
| 815·인포·일행 | 10/5(월) | 월·화·수·목·금 + 월(2회차) | ✅ 여유 있음 |
| 프리미엄 | **10/6(화)** | 화·수·목·금·월 | ✅ 전 요일 커버 |

**프리미엄 자료 마지노선이 10/6 → 10/2 로 당겨진다.** 10/6(화)에 발송을 시작해야 화요일 그룹이

10/9(금) 시작이 되고, 화요일 그룹의 첫 발송은 10/13 — 되돌릴 수단이 없는 날이 된다.

**88로또는 이 마지노선과 무관하다 — 현장 확답(9/24).** "12일 정지는 대표님 말씀대로 **88 제외
전산** 맞습니다." 10/12 자정에 사라지는 것은 이전 업체 전산이고, 88로또가 지금 쓰는 것은 바틀이
만든 88 전산이다. 우리가 통제하므로 10/13 첫 발송이 잘못되면 되돌릴 수 있다.

**도메인도 10/12 전에 끝나야 한다.** 회원용 홈페이지가 전산과 함께 삭제되므로(D194), 10/8~9 연결
일정은 유지하되 버퍼가 하루 줄었다.

## 8. 88로또 이관 도구 — 만들었다 (9/25)

9/24 에 "이 저장소에 없다"고 적었던 항목이다. **형제 저장소 `88lotto` 도 확인했고 거기에도
없었다**(`scripts/` 에 build-logic-doc.cjs · seedSupabase.ts · tests 뿐). 9/21 현장에 "제작을
마쳤습니다"라고 알린 것은 사실과 달랐다. 10/12 에 없으면 그날 만들 수 없으므로 연휴 중에
만들어 두었다 — `scripts/migrate-88lotto.py`.

### 왜 다른 세 사이트와 다른가
업체 SQL 덤프가 아니라 **스키마가 같은 우리 전산**에서 읽는다. 양쪽 `0001_schema.sql` 의
등급·상태·결제수단 enum 이 **완전히 동일**함을 확인했다(`grade`, `member_status`,
`payment_status`, `payment_method`). 그래서 815·인포·일행에서 제일 위험했던 "등급·상품 추측"이
88 에는 아예 없다. 프리미엄이 §7 때문에 막혀 있는 것과 대조적이다.

대신 세 가지가 어렵고, 도구는 그 세 가지를 위해 있다.

| 어려운 점 | 도구가 하는 일 |
|---|---|
| 옮기는 동안에도 88 화요일 발송이 돈다 | 1차 이관 → 2차 변경분 두 번 실행. 재실행해도 중복 생성되지 않는다(원본 id 기반 고정 id) |
| **양쪽 모두의 회원인 사람이 있다** | 넣기 전에 골라내 `번호 충돌`로 보고. 자동 병합하지 않는다 |
| 담당자·팀·상품 id 가 88 쪽 값이다 | 담당자는 login_id→이름 순으로 매칭, 팀은 이름. 못 맞추면 비우고 건수 보고 |

### ⚠️ 번호 충돌 — 이관 당일에 처음 겪으면 안 되는 것
같은 전화번호의 `members` INSERT 는 트리거 `enforce_member_admin_ops` 가 **거부한다**.
마이그레이션 주석에 "시스템 경로(service_role/SQL Editor)는 권한 검사만 면제하고 **중복 차단은
동일 적용**한다"고 못박혀 있다 — service role 키로도 뚫리지 않는다. 200행 묶음으로 넣으므로
충돌 1건이 그 묶음 전체를 실패시킨다. 88 과 플러스로또 양쪽 회원인 사람은 실제로 있을 수밖에
없으므로, 도구는 **대조 단계에서 전부 골라내고 아예 시도하지 않는다.** 합칠지 말지는 사람이
정한다(815 중복계약 처리와 같은 성격).

### 실행 순서
```
python3 scripts/migrate-88lotto.py --plan     # 1차 대조, 쓰기 없음
python3 scripts/migrate-88lotto.py --apply    # 1차 이관
python3 scripts/migrate-88lotto.py --plan     # 2차 변경분 대조
python3 scripts/migrate-88lotto.py --apply    # 2차 변경분 반영
```
원본(88) 접속은 **어느 모드에서도 구조적으로 읽기 전용**이다(GET 외 예외). 키는 환경변수로만
받는다 — `LOTTO88_SUPABASE_URL` · `LOTTO88_SERVICE_ROLE_KEY` · `VITE_SUPABASE_URL` ·
`SUPABASE_SERVICE_ROLE_KEY`. `--help` 에도 키 옵션을 띄우지 않는다(셸 기록에 남기지 않기 위함).

### 2차 실행이 건드리지 않는 것
이름·번호·등급·상태·정지/삭제/탈퇴와 `end_date`·발송요일·조합갯수만 따라간다.
**담당자·상담상태·메모·팀·유입코드는 따라가지 않는다** — 이관 후 플러스로또에서 운영진이 손댄
값을 88 쪽 값으로 되돌리면 안 된다. **조합발송 보류 상태도 따라가지 않는다**: 검수 후 해제한
회원이 2차 실행으로 다시 잠기면 문자가 조용히 끊기고, 반대면 미검수 회원에게 문자가 나간다.
`meta` 는 덮어쓰지 않고 병합한다. 이 회귀가 테스트 첫 항목이다
(`scripts/test_migrate_88lotto.py`, 20건, CI 등록).

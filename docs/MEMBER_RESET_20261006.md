# DB 초기화와 발급번호 보존 경계

2026-10-06 현장 요청: DB 초기화 시 회원 화면의 발급번호도 함께 비운다.

## 변경

- 활성 최고관리자만 `admin_reset_members`를 실행한다. 선택 1~500명은 하나의 트랜잭션으로 처리한다. 회원이 누락되거나 이력 형식·배정 로그·감사 로그 저장에 문제가 있으면 전원 롤백한다.
- 회원의 기존 초기화 항목과 함께 `weekly_recos`를 비운다. 원본 발급번호는 일반 운영 계정이 직접 읽거나 수정할 수 없는 `member_reco_reset_archive`에 그대로 남긴다. 콜메모 보존 규칙은 유지한다.
- 결제, 문자 접수, 추천 발급원장, 당첨 문자 outbox는 삭제하거나 성공/실패를 바꾸지 않는다. 초기화는 이미 요청한 문자 발송을 취소하지 않는다. 미확정 추천 발송(claimed/unknown) 또는 대기·진행·응답불명 당첨 문자가 있으면 초기화를 거부한다.
- 추천 선점 RPC는 화면뿐 아니라 초기화 보관 이력의 모든 회차를 검사한다. 직접 meta를 저장하는 기존 클라이언트도 trigger가 같은 회차 복원을 막는다. 추천 dryRun도 보관된 회차를 발급 가능으로 표시하지 않는다.
- 초기화 이전 당첨 집계 snapshot이 남아 있어도 회원 추천 분기는 보관된 회차를 다시 집계하거나 문자 outbox에 넣지 않는다. 원본 베팅과 베팅 집계는 이번 발급번호 초기화와 별개이며 그대로 보존한다.
- 출처·이관 식별자·추천 보류·발송 요일/개수·당첨 문자 회차 등 명시되지 않은 meta는 그대로 둔다.
- 동일 operation UUID로 불명확한 응답을 재확인하면 같은 초기화를 반복하지 않는다. 같은 UUID의 회원 명단이나 실행자를 바꾸면 거부한다.

## 적용 및 확인

1. 추천 발급 선점 migration과 durable lotto sync가 선행 적용된 환경에서 새 migration을 먼저 적용한다.
2. 프런트와 weekly-reco API를 배포한 뒤 운영 화면을 새로고침한다. RPC가 없으면 클라이언트는 이전 비원자 초기화로 돌아가지 않는다.
3. 합성 PostgreSQL의 권한·동시 실행·전체 롤백·재발급 차단과 UI/로직 테스트 및 빌드 결과를 확인한다. 실제 고객을 초기화해 검수하지 않는다.
4. 운영 DB 적용·실계정 확인은 별도 증거로 기록한다. 이 문서와 테스트 성공만으로 운영 배포 완료를 뜻하지 않는다.

## 복구

기존 원장과 archive/receipt는 롤백 배포에서도 삭제하지 않는다. 문제가 있으면 DB 초기화 UI를 중지하고 오류 원인을 점검한다. 과거 클라이언트로 복귀해 초기화 작업을 수행하면 원자성·표시 일관성을 잃을 수 있으므로 사용하지 않는다. 원본 issue를 회원의 활성 weekly_recos로 직접 복구하는 작업은 재발급 방어 trigger가 거부한다. 필요한 복구는 별도 승인 및 원장 대조 후 수행한다.

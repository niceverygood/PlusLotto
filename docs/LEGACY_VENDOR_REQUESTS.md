# 이전 전산업체 추가 요청 목록

> 현장 8/21 정의현 차장 질문 — "이전 전산업체에게 디비관련 추가 요구사항이 있을까요?"
> 근거: `infolotto_유료회원_SQL덤프_20260821.tar.gz` 실물 점검 + 815로또 코드대응표.
> **이 문서는 그대로 업체에 전달할 수 있게 썼다.** 사이트마다 같은 내용을 요청하면 된다.

## 먼저 — 좋은 소식

인포로또 덤프의 테이블 구조가 **815로또와 완전히 동일**하다(같은 개발사 `xenasia`).
5개 테이블·컬럼명이 한 글자도 다르지 않다. 그래서 **변환 프로그램을 사이트마다 새로 만들 필요가
없다.** 한 벌로 6개 사이트를 다 처리한다. 나머지 4개도 같은 구조로 오면 사이트당 작업이
"덤프 받아서 돌리고 건수 대조" 수준으로 줄어든다.

→ 그러므로 업체에 할 요청도 **6개 사이트 공통 1장**이면 된다.

## A. 반드시 받아야 하는 것 (없으면 기능이 죽는다)

### A-1. 상담원 명단 ★ 가장 중요
회원·결제 테이블에 `salesIdx`(담당 상담원), `salesRealIdx`(실제 매출 귀속), `salesLowIdx`·
`salesHighIdx`(상·하위 귀속), `groupTeamIdx`(팀), `insertUserIdx`·`updateUserIdx`(작성자)가
들어 있는데 **이 번호가 누구인지 알려주는 테이블이 덤프에 없다.**

받아야 할 것: 상담원 목록 — `idx, 이름, 로그인아이디, 직급/권한, 재직여부`

**8/24 실물 확인 — 815 기준 상담원은 111명이고, 미배정 회원은 3명뿐이다.**
즉 대응표만 받으면 13,234명의 담당이 그대로 살아난다. 없으면 전부 손으로 배분해야 한다.
우선순위 1번인 이유다.

> ~~팀 목록~~ 은 요청할 필요가 없다 — `groupTeamIdx` 가 13,237행 전부 0이라 팀 정보 자체가 없다.

### A-2. 상품 정보 — 우선순위 내려감 (8/24)
`itemCode`(family/mania/first)는 회원·결제에 들어 있고 상품 마스터는 없다. 다만 실물을 보니
**주당 조합 수·이용기간·결제액이 회원마다 개별값**이라(등급×조합수 조합만 17가지) 상품 마스터가
있어도 그대로 쓸 수 없다. **회원·결제의 실제값을 옮기는 것이 정답이다.**

그래도 받아두면 좋은 것: 상품 목록 — `itemCode, 상품명, 표준 판매가, 표준 이용개월수, 부여등급`
→ 우리 `products` 를 만들 때 이름·기준가로 쓴다. **없어도 이관은 진행할 수 있다.**

### A-3. 코드대응표 (5개 사이트분)
815로또는 `코드대응표.xlsx`(등급·상품 / 회원상태 / 결제 / 문자유형 / 컬럼사전 8시트)를 줬다.
**같은 것을 나머지 5개 사이트에도 요청한다.** 구조가 같으니 값만 다를 것이고, 업체 입장에서도
부담이 적다. 특히 아래 4개 코드의 값 목록이 필요하다.

`levelNum`(등급) · `statCode`(회원상태) · `statTmCode`(상담상태) · `payMethodCode`(결제수단)

### A-4. `statAdmCode` 의 의미 (8/24 신규)
대응표에 없던 컬럼인데 13,206행에 값이 있다 — `new` 9,942 / `2dayAbsence` 1,426 /
`2dayRefusal` 727 / `3day` 626 / `old` 485. **아웃콜 진행 단계로 추정**되고, 그렇다면
우리 아웃콜 관리(미아웃콜 세그먼트)에 그대로 연결된다. 한 줄 설명을 받는다.

### A-5. 유입코드 목록 — **`inflowFromCode` 하나만** (8/24 범위 축소)
실물을 보니 `inflowUniqCode`·`inflowTypeCode`·`inflowDevice` 는 **전부 빈값**이고,
값이 있는 것은 **`inflowFromCode` 191종** 하나뿐이다. `매체-캠페인` 형태로 보인다
(`rd-news` 1,661 / `ta-news` 1,129 / `dv-pro` 831 / `yn-auth` 548 …).

받아야 할 것: **`inflowFromCode` 191개 값의 뜻**(어느 매체·대행사·캠페인인지).
없으면 유입 분류가 알 수 없는 문자열로 들어가 유입별 매출 분석이 불가능하다.

## B. 확인만 하면 되는 것

### B-1. "전체회원"도 필요한가 — ✅ 확정 (8/21 정의현)
> "기존 사이트에서의 이전은 **유료 회원들만** 진행됩니다."

지금 받은 덤프(유료회원만)로 충분하다. 전체회원 덤프를 다시 받을 필요 없다.
현장이 말한 "전체회원 탭"은 **6개 사이트 유료회원을 한 화면에 모아 보는 탭**이라는 뜻이다
→ `meta.source_site` + 저장된 뷰로 해결(`MIGRATION_LEGACY_SITES.md` §0.2).

### B-2. 이미 한 번 이전된 회원이 있는가 — ✅ 해소 (8/24 실물 확인)
`convKey`·`convSvcName` 이 13,237행 **전부 빈값**이다. 815에는 전환 이력이 없다.
업체에 물을 필요 없다. (나머지 사이트는 덤프가 오면 같은 방식으로 확인한다.)

### B-3. 문자 발송 내역(pushSms) — ❌ 내 권고가 틀렸다. **이관한다** (8/25 현장 정정)

> 정의현 차장: "문자발송 내역은 저희가 **전산 운영하면서 사용해야될 필수 자료**인데,
> 그부분은 삭제하시면 안됩니다."

**D164~D168 에서 일관되게 "미이관 권고"라고 썼던 것을 철회한다.** 나는 용량(815 기준 855MB,
전체의 85%)만 보고 "과거 발송 이력은 운영에 거의 쓰이지 않는다"고 판단했는데, 현장은 이걸
**운영 필수 자료**로 쓴다. 고객이 "그 문자 언제 받았냐"고 물을 때 근거가 되는 자료다.
용량은 이관하지 않을 이유가 되지 못한다.

**지금 방침**: 회원·결제를 먼저 넣고(1차), **문자발송 내역도 반드시 이관한다**(2차).
대표님 지시로 전달만 나눠 받는다 — "일단 문자발송내역 뺀거를 별도로 받아주세요"(8/21).
즉 **빼서 받는 것은 전달 편의일 뿐 폐기가 아니다.** 원본 `pushSms` 파일은 보관한다.

| 사이트 | 문자 건수 | 압축 |
|---|---:|---:|
| 815로또 | 1,517,968 | 131.7MB |
| 인포로또 | 100,266 | 8.7MB |

**적재 가능성 확인함**: 우리 `sms_sends` 는 `member_id`·`sent_at` 인덱스가 있어(0001_schema)
151만 건이 들어가도 회원 상세의 문자 히스토리 조회에 문제가 없다.

**pushSms → sms_sends 매핑**

| 815 | 플러스로또 | 비고 |
|---|---|---|
| `userIdx` | `member_id` | `members.meta.legacy_idx` 로 역참조 |
| `to` | `phone` | |
| `contents` | `body` | |
| `contentsTypeCode`·`typeCode` | `type` | `sms_type` enum 6종(join·recommend·win·terms·marketing·direct)에 대응. **대응표 필요 ★** |
| `resultYN`·`statCode` | `status` | |
| `insertDateTime` | `sent_at` | |
| `api`·`apiId`·`apiKey` | — | **이관 금지**(연동 키, §C) |

★ `contentsTypeCode` 의 값 목록과 뜻을 업체에서 받아야 우리 6종에 정확히 대응된다.
받기 전에는 전부 `direct`(직접입력)로 넣고 나중에 재분류하는 것도 가능하다.

**⚠️ 저장 용량은 별도로 확인이 필요하다.** 815 하나가 Postgres 기준 대략 1GB 안팎으로
예상되고, 6개 사이트를 다 넣으면 수 GB다. Supabase 요금제 디스크 한도를 초과하면
비용이 오른다 — 적재 전에 현재 사용량과 한도를 확인한다. 초과하면 ① 요금제 상향
② 최근 N년만 적재하고 나머지는 원본 보관 중에서 고른다. **대표님 판단 사항.**

## C. 보안 — 업체에 알리고 조치할 것 ⚠️

결제 테이블에 **PG 연동 키와 비밀번호가 실제 값으로 들어 있다.**

```
payPw, payKey, payHash, payupApiKey, welcomepayApiKey, welcomepayIv,
payringApiKey, shvanApiKey, paysharpKey, 그리고 회원 테이블의 pw / pwTemp
```

- 이 컬럼들은 **이관 대상이 아니다.** 우리 쪽에는 넣지 않는다.
- 덤프 파일이 카톡·메일·드라이브를 돌아다녔으므로, **해당 PG사 연동 키는 교체를 권고**한다.
  (페이업·웰컴페이·페이링·쉬브이에이·페이샵 등 사용 중인 PG)
- 다음 사이트부터는 **이 컬럼들을 빼고 추출**해 달라고 요청한다.
- 회원 비밀번호(`pw`)도 이관하지 않는다. 이관 회원은 최초 로그인 시 재설정한다.

## D. 파일 전달 방법 — 한 파일 30MB 제한 (8/21 질문)

> "sql 을 30메가씩 자르면 되는건지, 압축파일을 30메가 단위로 자르면 되는건지"
>
> **✅ 해결됨 (8/24)** — 업체가 아래 2순위 방식(테이블별 개별 압축 + pushSms 제외)으로
> 815 를 다시 보내왔다. **148MB → 23MB.** 자를 필요가 없었다.
> 나머지 사이트도 같은 방식으로 요청한다.

**답: 둘 다 아니고, 자르지 않는 방법이 있다.** 아래 순서로 시도한다.

### 1순위 — pushSms 를 **따로** 받아 달라 (파일을 나누는 것이지 빼는 게 아니다)
압축 후 용량의 62%가 문자 발송 내역이다. 이것만 분리하면 나머지가 **38%로 줄어**
30MB 제한에 걸리지 않는다.

> ⚠️ **폐기가 아니다.** 8/25 현장 확인으로 문자 발송 내역도 **이관 대상**이 됐다(§B-3).
> 파일만 나눠 받아 회원·결제부터 먼저 작업하고, 문자는 2차로 넣는다. 원본은 보관한다.

### 2순위 — 테이블별로 따로 압축해 달라 (그래도 넘으면)
지금도 압축 안에 테이블별 파일 5개로 나뉘어 있다. 이걸 **하나로 묶지 말고 각각 따로**
보내달라고 하면 된다. 인포로또 기준 가장 큰 파일이 8.7MB 라 어떤 사이트든 30MB 를 넘기 어렵다.

```
infolotto_schema.sql.gz              ← 테이블 구조
infolotto_user.sql.gz                ← 0.6MB
infolotto_payment.sql.gz             ← 0.3MB
infolotto_userMemo.sql.gz            ← 3.9MB
infolotto_gameBettingNlotto.sql.gz   ← 0.6MB
```

**이 방식이 분할보다 나은 이유: 각 파일이 그 자체로 완결이라 다시 붙일 필요가 없다.**
조각 하나가 누락되거나 순서가 틀릴 위험이 아예 없고, 필요한 테이블만 먼저 받아 작업을
시작할 수도 있다.

### 3순위 — 그래도 안 되면 **압축파일**을 자른다 (SQL 텍스트가 아니라)
질문에 답하자면 **압축파일 쪽**이다. SQL 텍스트를 30MB 씩 자르면 각 조각이 혼자서는 못 쓰는
파일이 되고(INSERT 문 머리가 첫 조각에만 있다), 다시 붙일 때 순서가 틀려도 오류 없이
조용히 깨진 데이터가 들어간다. 압축파일 분할은 순서대로 이어붙이면 원본과 바이트 단위로 같다.

업체 쪽 명령:
```bash
split -b 25m ilhanglotto_유료회원_SQL덤프.tar.gz ilhanglotto_part_
sha256sum ilhanglotto_유료회원_SQL덤프.tar.gz   # 이 값도 같이 보내달라고 한다
```
받는 쪽:
```bash
cat ilhanglotto_part_* > ilhanglotto_유료회원_SQL덤프.tar.gz
sha256sum ilhanglotto_유료회원_SQL덤프.tar.gz   # 위 값과 같아야 한다
```
**해시값을 반드시 같이 받는다.** 조각 하나가 빠져도 `cat` 은 오류를 내지 않는다.
25MB 로 자르는 이유는 30MB 가 상한이라 여유를 두기 위해서다.

## E. 우리 쪽에서 정해야 하는 것 (업체와 무관)

`docs/MIGRATION_LEGACY_SITES.md` §4 참조 — 등급 대응, 아이디 충돌, 전화번호 중복, 상품 생성.
**사이트가 6개가 되면서 하나가 더 늘었다: 사이트 간 중복 회원.** 인포로또는 4,403명 전원이
휴대폰 번호를 갖고 있어(평문, 100%) 번호 기준 대조가 가능하다. 6개를 합쳤을 때 같은 사람이
여러 사이트에 있으면 **등급·종료일·담당을 누구 것으로 남길지** 규칙이 필요하다.

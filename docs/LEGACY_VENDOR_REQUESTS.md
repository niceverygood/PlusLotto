# 이전 전산업체 추가 요청 목록

> 현장 8/21 정의현 차장 질문 — "이전 전산업체에게 디비관련 추가 요구사항이 있을까요?"
> 근거: `infolotto_유료회원_SQL덤프_20260821.tar.gz` 실물 점검 + 815로또 코드대응표.
> **이 문서는 그대로 업체에 전달할 수 있게 썼다.** 사이트마다 같은 내용을 요청하면 된다.

## 먼저 — 좋은 소식

인포로또 덤프의 테이블 구조가 **815로또와 완전히 동일**하다(같은 개발사 `xenasia`).
5개 테이블·컬럼명이 한 글자도 다르지 않다. 그래서 **변환 프로그램을 사이트마다 새로 만들 필요가
없다.** 한 벌로 6개 사이트를 다 처리한다. 나머지 4개도 같은 구조로 오면 사이트당 작업이
"덤프 받아서 돌리고 건수 대조" 수준으로 줄어든다.

→ 그러므로 업체에 할 요청도 **6개 사이트 공통 1장**이면 된다.

## A. 반드시 받아야 하는 것 (없으면 기능이 죽는다)

### A-1. 상담원·팀 정보 ★ 가장 중요
회원·결제 테이블에 `salesIdx`(담당 상담원), `salesRealIdx`(실제 매출 귀속), `salesLowIdx`·
`salesHighIdx`(상·하위 귀속), `groupTeamIdx`(팀), `insertUserIdx`·`updateUserIdx`(작성자)가
들어 있는데 **이 번호가 누구인지 알려주는 테이블이 덤프에 없다.**

받아야 할 것: 상담원 목록 — `idx, 이름, 로그인아이디, 팀, 직급/권한, 재직여부`
받아야 할 것: 팀 목록 — `idx, 팀이름, 팀장 idx`

없으면 → **회원 담당자·팀·매출 귀속이 전부 비어서 들어간다.** 이관 후 15만 건을 손으로
다시 배분해야 한다. 우선순위 1번이다.

### A-2. 상품 정보
`itemCode`·`itemName`(예: family/mania/first)은 회원·결제에 들어 있는데 **상품 마스터가 없다.**

받아야 할 것: 상품 목록 — `itemCode, 상품명, 판매가, 이용개월수, 주당 조합 수(itemOptionSlot), 부여등급`

없으면 → 등급 대응과 주당 조합 발송 갯수를 추정으로 넣게 된다(= 고객 클레임).
815는 코드대응표에 이 내용이 있었으니, **나머지 5개 사이트도 815와 같은 형식의 코드대응표를
달라**고 하면 한 번에 해결된다.

### A-3. 코드대응표 (5개 사이트분)
815로또는 `코드대응표.xlsx`(등급·상품 / 회원상태 / 결제 / 문자유형 / 컬럼사전 8시트)를 줬다.
**같은 것을 나머지 5개 사이트에도 요청한다.** 구조가 같으니 값만 다를 것이고, 업체 입장에서도
부담이 적다. 특히 아래 4개 코드의 값 목록이 필요하다.

`levelNum`(등급) · `statCode`(회원상태) · `statTmCode`(상담상태) · `payMethodCode`(결제수단)

### A-4. 유입코드 목록
`inflowUniqCode`, `inflowFromCode`, `inflowTypeCode`, `inflowAdAgency`, `inflowAdKeyword` 의
코드값 정의. 없으면 유입 분류가 알 수 없는 문자열로 들어간다.

## B. 확인만 하면 되는 것

### B-1. "전체회원"도 필요한가
지금 온 덤프는 **유료회원만**이다(파일 첫 줄에 `유료회원 4403명 / idx IN (…)` 으로 명시돼 있다).
현장에서 "전체회원 나올 수 있는 탭"을 요청했는데, 그 탭이 **무료·탈퇴 회원까지 포함**하는
뜻이라면 전체회원 덤프를 다시 받아야 한다. 유료회원 6개 사이트를 합친 목록이라는 뜻이면
지금 자료로 충분하다. → **현장 확인 먼저, 그 다음 업체 요청.**

### B-2. 이미 한 번 이전된 회원이 있는가
`convKey`, `convSvcCode`, `convSvcName`, `convSvcDateTimeEnd` 컬럼이 있다. 다른 서비스에서
넘어온 회원을 표시하는 칸으로 보인다. 사이트 간 중복 회원 판정에 영향이 있으니 무슨 뜻인지
한 줄 설명을 받는다.

### B-3. 문자 발송 내역(pushSms)은 빼도 되는가
용량의 대부분이 이것이다 — 815는 151만 건 855MB, 인포로또는 10만 건 51.7MB.
과거 문자 이력은 운영에 거의 쓰이지 않는다. **다음 사이트부터는 pushSms 를 빼고 달라**고 하면
전송·처리 부담이 크게 준다. (이미 받은 것은 그냥 두면 된다.)

## C. 보안 — 업체에 알리고 조치할 것 ⚠️

결제 테이블에 **PG 연동 키와 비밀번호가 실제 값으로 들어 있다.**

```
payPw, payKey, payHash, payupApiKey, welcomepayApiKey, welcomepayIv,
payringApiKey, shvanApiKey, paysharpKey, 그리고 회원 테이블의 pw / pwTemp
```

- 이 컬럼들은 **이관 대상이 아니다.** 우리 쪽에는 넣지 않는다.
- 덤프 파일이 카톡·메일·드라이브를 돌아다녔으므로, **해당 PG사 연동 키는 교체를 권고**한다.
  (페이업·웰컴페이·페이링·쉬브이에이·페이샵 등 사용 중인 PG)
- 다음 사이트부터는 **이 컬럼들을 빼고 추출**해 달라고 요청한다.
- 회원 비밀번호(`pw`)도 이관하지 않는다. 이관 회원은 최초 로그인 시 재설정한다.

## D. 우리 쪽에서 정해야 하는 것 (업체와 무관)

`docs/MIGRATION_LEGACY_SITES.md` §4 참조 — 등급 대응, 아이디 충돌, 전화번호 중복, 상품 생성.
**사이트가 6개가 되면서 하나가 더 늘었다: 사이트 간 중복 회원.** 인포로또는 4,403명 전원이
휴대폰 번호를 갖고 있어(평문, 100%) 번호 기준 대조가 가능하다. 6개를 합쳤을 때 같은 사람이
여러 사이트에 있으면 **등급·종료일·담당을 누구 것으로 남길지** 규칙이 필요하다.

## 부록 — 업체에 보낼 요약문 (복사용)

```
안녕하세요. 이관 작업 관련해 아래 자료를 추가로 요청드립니다.
6개 사이트 구조가 동일해서 사이트별로 같은 항목이면 됩니다.

1. 상담원 목록 (idx, 이름, 로그인아이디, 소속팀, 권한, 재직여부)
   - 회원/결제의 salesIdx, salesRealIdx 가 누구인지 알 수 없어 담당자와
     매출 귀속을 살릴 수 없습니다. 가장 급합니다.
2. 팀 목록 (idx, 팀명, 팀장)
3. 상품 목록 (itemCode, 상품명, 판매가, 이용개월수, 주당 조합 수, 부여등급)
4. 코드대응표 - 815로또에 주셨던 엑셀과 같은 형식으로 나머지 5개 사이트분
   (levelNum 등급 / statCode 회원상태 / statTmCode 상담상태 / payMethodCode 결제수단)
5. 유입코드 목록 (inflowUniqCode, inflowFromCode, inflowTypeCode, inflowAdAgency)

확인 부탁드릴 것:
6. convKey / convSvcCode / convSvcName 컬럼의 의미
7. 다음 덤프부터는 pushSms(문자발송내역) 테이블은 빼주셔도 됩니다.
   용량의 대부분을 차지하는데 저희 쪽에서 쓰지 않습니다.

보안 관련:
8. 결제 테이블에 PG 연동 키(payupApiKey, welcomepayApiKey, welcomepayIv,
   payringApiKey, shvanApiKey 등)와 payPw, payKey, payHash 가 실제 값으로
   들어 있습니다. 저희는 이관하지 않고 폐기하겠습니다만, 파일이 외부로
   전달된 만큼 해당 PG 연동 키 교체를 권해드립니다.
   다음 추출부터는 이 컬럼들을 제외해 주시면 감사하겠습니다.
```

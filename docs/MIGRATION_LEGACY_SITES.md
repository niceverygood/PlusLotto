## 0. 6개 사이트가 같은 시스템이다 — 이 프로젝트의 핵심 사실

인포로또 덤프의 테이블 구조를 815로또 대응표와 대조한 결과 **완전히 동일**하다.
같은 개발사(`xenasia`)가 만든 같은 패키지고, 5개 테이블 353개 컬럼이 한 글자도 다르지 않다.

| | 815로또 | 인포로또 |
|---|---|---|
| 테이블 | user·payment·userMemo·pushSms·gameBettingNlotto | **동일** |
| user 컬럼 | 152개 | **동일** |
| payment 컬럼 | 113개 | **동일** |
| 추출 조건 | 유료회원만, 결제는 `statCode='success'`, 조합은 `grade>0` | **동일** |
| 휴대폰 | 평문 | 평문 (4,403명 전원 보유) |

**결과: 변환 프로그램은 한 벌이면 된다.** 사이트별로 다른 것은 코드값(등급·유입코드)뿐이라
설정 파일로 분리하면 된다. 사이트가 6개라고 작업량이 6배가 되지 않는다.

> 먼저 넣고 문자는 2차로 넣는다. 자세한 매핑은 `LEGACY_VENDOR_REQUESTS.md` §B-3.

## 0.2 "전체회원 탭" — 사이트 출처를 남겨야 한다

**이관 대상은 유료회원만이다**(8/21 정의현 확정 — "기존 사이트에서의 이전은 유료 회원들만
진행됩니다"). 따라서 "전체회원 탭"은 무료·탈퇴 회원까지 포함하는 뜻이 아니라
**6개 사이트 유료회원을 한 화면에 모아 보는 탭**이다.

현장 요구: 사이트별 목록 + **전체회원을 모아 보는 탭**.
회원마다 어느 사이트에서 왔는지 남기지 않으면 이 탭을 만들 수 없다.

→ 이관 시 `meta.source_site` 에 사이트 키(`815`·`ilhang`·`info`…)를 넣고,
`features/members/views.ts` 의 저장된 뷰(§7) 에 사이트별 프리셋을 추가한다.
**새 구조가 필요 없다** — 26개 세그먼트를 돌리는 기존 뷰 패턴을 그대로 쓴다.

## 0.3 ★ 815 실물 덤프 검증 결과 (8/24) — 매핑이 여러 군데 틀렸다

업체가 요청대로 **테이블별 개별 압축 + pushSms 제외**로 다시 보내왔다(148MB → **23MB**).
13,237행 전체를 파싱해 대응표와 대조한 결과, **대응표의 상품 정의는 "정가·표준값"이고
실제 데이터는 회원마다 개별 조정돼 있다.** 등급에서 값을 파생하면 안 된다.

### 확인된 것 ✅
| 항목 | 결과 |
|---|---|
| 건수 | user 13,237 / payment 21,680 / userMemo 178,162 / 조합(당첨) 347,138 — 대응표와 일치 |
| `levelNum` ↔ `itemCode` | **완전 1:1** — 2=family 9,030 / 3=mania 3,640 / 4=first 567 |
| 휴대폰 | **13,237명 전원 정상 형식**(100%). 사이트 간 중복 대조 가능 |
| `statCode` | 전부 `normal` — 이관분은 전원 정상 상태 |
| `convKey`·`convSvcName` | **전부 빈값** → 「이미 이전된 회원」 우려 해소(§4 확인항목 닫힘) |

### 틀렸던 것 ❌ — 반드시 고쳐서 이관한다
1. **주당 조합 수(`itemOptionSlot`)를 등급에서 파생하면 안 된다.**
   등급×조합수 조합이 **17가지**다. 매니아인데 10개인 회원이 991명(매니아의 27%),
   패밀리인데 20개인 회원이 368명. 5·7·15·30·40개짜리도 있다.
   → **회원별 실제값을 그대로 옮긴다.** 파생하면 991명의 조합이 반토막 난다.
2. **이용기간(`itemExpMonth`)도 파생 금지.** 13종이다(36·20·18·21·26·24·27·19개월…).
   대응표의 "패밀리 18개월 / 매니아·퍼스트 36개월"은 표준값일 뿐이다.
3. **판매가는 대응표 값을 쓰면 안 된다.** 대응표는 488,000 / 7,880,000 / 11,880,000 원인데
   실제 결제액 최빈값은 216,000 / 214,000 / 212,000 원이다(총 매출 128.9억, 건당 평균 59.5만).
   → **`itemWon` 실제값만 쓴다.**
4. **`salesRealIdx` 는 21,680건 전부 0** — 쓸 수 없다. 매출 귀속은 `salesIdx` 하나뿐이다.
5. **`inflowUniqCode`·`inflowTypeCode`·`inflowDevice` 는 전부 빈값.**
   값이 있는 유입 컬럼은 **`inflowFromCode` 하나(191종)** 뿐이다. `매체-캠페인` 형태
   (`rd-news` `dv-pro` `ta-news` …). 유입코드 요청 대상을 이 하나로 좁힌다.
6. **`groupTeamIdx` 전부 0** — 팀 정보가 없다. 업체에 팀 목록을 요청할 필요가 없다.
7. **`tmLevel`·`absence`·`pointTotal`·`moveCode` 전부 0, `email` 13건뿐** — 이관 대상 아님.

### 새로 발견 — 매핑이 필요한 컬럼
**`statAdmCode`** (13,206행에 값, 6종): `new` 9,942 / `2dayAbsence` 1,426 /
`2dayRefusal` 727 / `3day` 626 / `old` 485. 아웃콜 진행 단계로 보인다.
우리 아웃콜 플래그(§8)와 연결될 후보라 **의미 확인이 필요하다**.

### ★ 운영에 바로 영향을 주는 두 가지
1. **조합 발송요일이 월~금에 흩어져 있다** — mon 3,213 / tue 2,804 / wed 2,805 /
   thu 2,573 / fri 1,841. 토·일은 없다. 우리 기본값(금요일 `DEFAULT_RECO_DAY=5`)으로
   일괄 입력하면 **금요일 하루에 13,237건이 몰린다.** 회원별 요일을 그대로 옮겨야 한다
   (`mon`=1 … `fri`=5).
2. **90일 안에 3,301명(25%)이 만료된다.** 이미 만료된 회원도 111명 있다.
   이관 직후 곧바로 재계약 아웃콜 대상이 된다 — 현장에 미리 알려야 한다.
   (종료일 분포: 2026년 4,935 / 2027년 6,209 / 2028년 2,063 / 2029년 30)

### 그 밖의 실측치
- **담당 상담원 111명**(결제 귀속은 110명). 미배정은 3명뿐 — 대응표만 받으면 담당이 거의 다 살아난다.
- 결제수단은 2종뿐: `officeCredit`(수기-단말기) 16,966 / `siteBank`(무통장) 4,714. PG 결제 없음.
- **회원 4,372명(33%)이 2건 이상 결제**(최다 23건) → 결제는 이력 전체를 옮기고
  종료일은 **가장 최근 결제 기준**으로 잡는다.
- 당첨: 1등 2건 · 2등 4건 · 3등 320건 · 4등 18,827 · 5등 327,985. 당첨금 합계 64.6억.
  1~3등 당첨 회원 323명 → 이 사람들만 뽑아도 당첨자 세그먼트가 산다.
- 상담메모 상담상태: `success` 153,137 / `chance` 17,766 / `absence` 6,076 /
  `refuse` 455 / `manageFree` 290(우리에 없음 → 기타). 회원당 평균 13.5건, 최다 148건.

## 0.4 ★ 4사 코드대응표 수령 (8/31) — 사이트마다 등급 체계가 다르다

업체가 `로또4사_코드대응표_20260826.xlsx`(7시트)를 보내왔다. **§4 미결 대부분이 여기서 풀렸다.**

**대상은 4사다**: `lotto815`(815korean) · `cplotto`(**=일행로또** ilhanglotto) · `infolotto` · `lotto88`(88로또).

`lotto88` 은 이미 우리 전산이라 이관 대상이 아니다(8/27 확정).

### `statAdmCode` — 정의 확보(§A-4 해소). 우리 아웃콜 관리와 연결된다
**"DB 를 언제 받았고 어떤 상태인가"를 나타내는 관리자용 분류**로, 상담 단계(`statTmCode`)와 별개다.

`new` 신규(접촉 전) · `old` 구디비 · `3day` 이틀전 배정 ·
`2dayAbsence` 하루전 부재 → **팀에 신디비로 재투입** · `2dayRefusal` 하루전 거절 → **재투입**

재투입 개념이 우리 「초기화(재사용) DB」와 같은 자리다(D-자동할당). `meta.legacy_stat_adm` 으로
보관하고 세그먼트 연결은 현장 확인 후 정한다.

### 유입코드 — **정해진 목록이 없다**(§A-5 해소)
`inflowFromCode` 는 **운영자가 직접 입력하는 자유 문자열**이다. 관리자 화면이 DB 에 이미 있는 값을
선택지로 보여줄 뿐, 코드가 곧 라벨이고 정해진 뜻이 없다(4사 전체 501종, 815 덤프 191종).
→ **변환 없이 문자열 그대로 옮긴다.** 의미 확인은 이관과 무관하게 사내에서 하면 된다.

### 문자유형 — 고정 8종 + 회차별 202종(D171 보강)
D171 은 인포로또만 보고 6종을 확정했는데, 4사 전체로는 **고정 8종**이다. 추가된 2종을 반영한다.

`autoPick`→`recommend` · `nlottoWin{회차}`→`win` · `admin`→`direct` · `thankCharge`→`join` ·
`adminPickSend`→`recommend` · `autoPickRecovery`→`recommend` ·
**`autoPickReSend`(조합 재발송)→`recommend`** · **`adminSettinSend`(관리자 설정 발송)→`direct`** ·
`userPwMofiy`(비밀번호 변경 안내, 4사 합쳐 2건)→`direct`

회차 범위는 1034~1237 이다.

### ★ 새로 드러난 문제 — 덤프에 과거 유료회원이 빠져 있다
대응표의 `freeYN='N'`(유료회원) 집계와 덤프 행수가 다르다.

| 사이트 | 유료회원 전체 | 덤프에 담긴 수 | 차이 |
|---|---:|---:|---:|
| 815korean | 21,809 | 13,237 | **-8,572** |
| infolotto | 5,078 | 4,403 | -675 |

덤프는 "현재 이용중" 유료회원만 담은 것으로 보인다. 빠진 8,572명은 **과거에 결제했다가 만료된
회원** — 재계약 영업 대상이다. **이들도 이관할지 확인이 필요하다**(§4-8).

> 완전 1:1 로 확인됐다. 등급 대응만 정하면 되고, 나머지 값은 회원별 실제값을 옮긴다.

## 4. 먼저 정해야 할 것 (막히는 지점)

1. **★ 등급 대응** — §2.1 제안대로 갈지. 잘못되면 조합 발급 수와 매출 분류가 전부 틀어진다.
2. ~~**★ 담당 상담원(`salesIdx`)**~~ — **경로 확정(8/31).** `salesIdx` 값 110개가 전부 `user` 테이블
   채번 범위(최대 788,875 < AUTO_INCREMENT 790,047) 안이고 유료회원과는 1개만 겹친다 →
   **상담원은 같은 `user` 테이블에 있고, "유료회원만" 추출 조건 때문에 빠진 것**이다.
   업체에 그 110행의 `idx, id, name` 만 추가로 요청하면 된다(`LEGACY_VENDOR_REQUESTS.md` §A-1).
   현장에서 받은 `관리자_아이디.xlsx`(41명, 이름↔아이디)는 **우리 쪽 상담원 명부**라
   저쪽 `idx` 와 잇는 다리가 아니다 — 이름으로 맞춘다. 명단에 없는 담당자는 관리자로 배정(현장 지시).
3. **★ 로그인 아이디** — 815 `id` 를 그대로 쓰면 기존 플러스로또 회원과 충돌할 수 있다.
   충돌 시 `pl####` 새 채번으로 넘기고, 원본 id 는 `meta.legacy_id` 에 보관하는 방식을 제안한다.
4. **전화번호 중복** — 우리 DB에 이미 있는 번호는 트리거가 INSERT 를 막고 기존 회원을 '중복 DB'로
   표시한다(D-중복가드). 이관분은 **덮어쓰지 않고 건너뛴 뒤 목록으로 보고**하는 것이 안전하다.
5. **상품(`products`)** — 815 상품 4종을 우리 `products` 에 만들지, 기존 상품에 붙일지.
6. **★ 사이트 간 중복 회원** — 사이트가 6개가 되면서 새로 생긴 문제다. 같은 사람이 여러
   사이트에 있으면 **등급·종료일·담당상담원·결제이력을 누구 것으로 남길지** 규칙이 필요하다.
   인포로또는 4,403명 전원이 휴대폰 번호를 갖고 있어 번호 기준 대조는 가능하다.
   제안: **한 명으로 합치되 등급은 높은 쪽, 종료일은 늦은 쪽, 결제이력은 전부 승계**하고
   합쳐진 흔적을 `meta.merged_from` 에 남긴다. 담당은 최근 결제한 사이트 기준.
8. **★ 과거 유료회원(만료자) 이관 여부** — 덤프는 현재 이용중인 유료회원만 담고 있다.
   815 기준 8,572명이 빠져 있고 이들은 재계약 영업 대상이다. 받을지 결정해야 한다(§0.4).
7. **비밀번호·PG 키 미이관** — 덤프에 회원 비밀번호와 PG 연동 키가 평문으로 들어 있다.
   둘 다 넣지 않는다. 이관 회원은 최초 로그인 시 비밀번호 재설정. 자세한 내용은
   `LEGACY_VENDOR_REQUESTS.md` §C.

## 5.6 적재 도구 — `scripts/load-legacy-site.py` (8/31)

현장 요청("일단 815부터 입력해주셔서 사용하도록 할수있는 방법은 가능한가요?")에 대한 답이다.
**개발 세션에는 라이브 Supabase 키가 없다** — 키를 가진 쪽에서 직접 돌린다(키가 밖으로 나가지 않는다).

```
# 1) 무엇이 들어갈지만 본다 (DB 접속 안 함)
python3 scripts/load-legacy-site.py --site lotto815 --dir ./815 --dry-run
# 2) 100건 시범 적재 → 화면에서 눈으로 확인
python3 scripts/load-legacy-site.py --site lotto815 --dir ./815 --url ... --key ... --limit 100
# 3) 전체
python3 scripts/load-legacy-site.py --site lotto815 --dir ./815 --url ... --key ...
```

- **재실행 안전** — `meta.legacy_idx` 로 이미 들어간 회원을 알아보고 건너뛴다.
- **전화번호 중복은 건너뛰고 보고**한다(덮어쓰지 않는다). 로그인 아이디가 겹치면 새 아이디를
  부여하고 원본은 `meta.legacy_login_id` 에 남긴다.
- **담당 상담원은 `meta.legacy_sales_idx` 에 원본 번호로 보관만** 한다 → 대응표가 오면 그때
  일괄 배정하면 되고, **대응표를 기다리느라 적재를 미룰 필요가 없다.**
- 등급·이용기간·주당조합·결제액은 회원별 실제값을 쓴다(D167).

**모의 실행 검증(실제 덤프)**: 815 → 13,237명(goldp 9,030·vip 3,640·royal 567) / 결제 21,680건
128.9억 / 발송요일 월3,213·화2,804·수2,805·목2,573·금1,841 — D167 실측치와 정확히 일치한다.

> ⚠️ **적재 후에는 그 사이트 영업을 우리 전산에서만 해야 한다.** 구 시스템에서 계속 상담·결제가
> 일어나면 데이터가 두 곳으로 갈라지고, 나중에 그 기간분을 다시 받아 덧붙여야 한다(델타 재적재).

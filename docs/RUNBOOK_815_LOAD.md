# 815 이관 실행 절차서

현장 우선순위(9/8 정의현 차장): **815 → 인포 → 일행 → 프리미엄**
자료 수령: 815 · 일행 · 인포 (9/8 15:40) · 프리미엄은 계약 확정 후

> **이 문서를 위에서 아래로 그대로 따라간다.** 각 단계 끝에 멈춤점이 있다.
> 멈춤점에서 결과를 확인하기 전에는 다음 단계로 가지 않는다.
> 8/31 사고(D177)는 확인 없이 이어서 실행했기 때문에 났다.

---

## 왜 이 순서인가 — 8/31에 무슨 일이 있었는지

그날 **데이터는 정상적으로 들어갔다.** 회원 19,829명, 결제 25,679건 모두 변환이 맞았다.
문제는 **들어갈 자리가 없었다**는 것이다.

지금 전산에서 사이트를 구분해 보여주는 곳은 **회원목록 한 군데뿐**이다.

| 화면 | 사이트 구분 |
|---|---|
| 회원목록 | 있음 (원본 사이트 필터) |
| 결제 관리 | **없음** |
| 매출 | **없음** |
| 대시보드 | **없음** |
| 통계 | **없음** |

그래서 815 데이터가 들어가는 순간 대시보드 신규유입이 뛰고, 결제 목록에 815 결제가 섞이고,
매출에 134억이 얹혔다. 정의현 차장이 본 "전산 이상합니다"가 이것이다.
**로더 버그가 아니라, 칸막이 없는 방에 손님을 들여보낸 것이다.**

9/1에 차장이 요구한 것도 정확히 이것이었다.

> "각각 88/815/일행 등 사이트별 독립적 대표번호부터 다릅니다.
> **회원들이 섞이면 안 되어서** 개별 사이트별로 관리할 수 있게 요청 드립니다.
> 전달드린 디비를 **사이트별로 드롭다운 클릭하면** 사이트별 관리할 수 있게 요청 드립니다."

그래서 **1단계(검증)와 2단계(칸막이)를 먼저 끝내고 3단계(적재)로 간다.**

# 1단계 — 데이터 검증 (지금 바로 가능 · DB 안 건드림)

DB에 접속하지 않고 파일만 읽는다. 아무것도 쓰지 않으므로 안전하다.
칸막이 작업과 **동시에 진행할 수 있다.**

## 1-1. 사전 점검

```bash
cd ~/PlusLotto     # 리포 위치에 맞게

bash scripts/preflight-legacy-load.sh \
  lotto815 \
  ~/Downloads/815korean_paid_all_20260831.zip
```

확인하는 것: python3, 적재 도구, ZIP 무결성, 덤프 파일 이름 규칙, 등급 대응표, 도구 단위 테스트.

**■ 멈춤점 1** — `점검 통과`가 나와야 다음으로 간다.
`실패 N건`이 나오면 그 항목을 먼저 해결한다. 경고(!)는 넘어가도 된다.

## 1-2. 무엇이 들어갈지 확인 (dry-run)


216MB를 읽으므로 몇 분 걸린다. 출력 마지막에 이 문구가 나온다.

> ※ 쓰기 없이 종료했습니다. 출력에는 키와 개인정보가 포함되지 않습니다.

**■ 멈춤점 2** — 출력 전체를 복사해서 공유한다. 개인 이름·전화번호는 나오지 않는다.
다음을 대조한다.

| 항목 | 8/31 실측값 | 이번 값이 다르면 |

| 원본 회원 | 21,809명 | 자료가 바뀐 것이다. 차장께 확인 |

# 2단계 — 칸막이 만들기 (적재 전 필수)

**이 단계를 건너뛰고 3단계로 가면 8/31이 그대로 재현된다.**

## 무엇을 만드는가

최상단에 사이트 드롭다운을 놓고, 고른 사이트로 **모든 화면**이 걸러지게 한다.

```
[ 전체 사이트 ▾ ]   ← 상단바
   전체 사이트
   플러스로또
   815로또
   인포로또
   일행로또
```

## 손대야 하는 것

프런트는 전역 상태(zustand) 하나와 상단바 드롭다운, 그리고 각 기능의 `api.ts`에서
선택된 사이트를 넘기는 배선이다. DB는 아래 RPC에 `p_source_site` 파라미터를 추가한다.

| RPC | 화면 |
|---|---|
| `admin_dashboard` | 대시보드 KPI |
| `admin_payments_page` · `admin_payment_counts` | 결제 관리 |
| `admin_revenue` · `admin_revenue_calendar` · `admin_revenue_day_payments` | 매출 |
| `admin_stats_snapshot` | 통계 |
| `admin_bets_page` | 베팅 |
| `admin_members_page` | 이미 `p_filter`로 지원 — 전역 선택과 연결만 하면 된다 |

`members.meta.source_site` 인덱스는 8/31에 이미 만들어 뒀다
(`20260831094500_legacy_import_provenance_and_source_filter.sql`). 성능 준비는 되어 있다.

**■ 멈춤점 3** — 칸막이 배포 후, 데이터를 넣기 전에 확인한다.
드롭다운에서 **플러스로또**를 골랐을 때 지금 보이는 숫자(회원 수·매출)가
**전체 사이트**를 골랐을 때와 같아야 한다. 아직 레거시 데이터가 없으므로 당연히 같아야 하고,
다르다면 필터가 잘못 걸린 것이다.

# 3단계 — 815 적재

1·2단계가 끝난 뒤에만 진행한다.

## 3-1. DB 접속 정보 준비

```bash
export VITE_SUPABASE_URL='https://...supabase.co'
export SUPABASE_SERVICE_ROLE_KEY='...'
```

> 이 키는 **모든 권한**을 가진다. 화면에 띄운 채로 화면 공유를 하지 않는다.
> 셸 기록에 남기지 않으려면 앞에 공백 하나를 넣고 입력한다.

사전 점검을 다시 돌려 접속 정보가 잡혔는지 확인한다.

```bash
bash scripts/preflight-legacy-load.sh lotto815 ~/Downloads/815korean_paid_all_20260831.zip
```

## 3-2. 기준값 기록 (원복의 근거)

적재 **전** 숫자를 남긴다. 문제가 생겼을 때 되돌릴 목표가 된다.

관리자 화면에서 다음을 적어 둔다.

- 전체 회원 수 (8/31 원복 후 기준: **47,205명**)
- 전체 결제 건수 (기준: **1,343건**)
- 이번 달 매출 금액·건수

## 3-3. 읽기 전용 대조 (plan)

```bash
python3 scripts/load-legacy-site.py \
  --site lotto815 \
  --archive ~/Downloads/815korean_paid_all_20260831.zip \
  --plan
```

DB를 **읽기만** 한다. 기존 회원과 전화번호가 겹치는 건이 몇 건인지 알려준다.
8/31에는 1,971명이 겹쳐서 제외됐다.

**■ 멈춤점 4** — 제외 건수가 8/31과 크게 다르면 멈추고 원인을 확인한다.

## 3-4. 시범 적재 (100명)

```bash
python3 scripts/load-legacy-site.py \
  --site lotto815 \
  --archive ~/Downloads/815korean_paid_all_20260831.zip \
  --limit 100 \
  --batch-id lotto815-20260908 \
  --apply
```

> **`--batch-id`는 반드시 넣는다.** 8/31에 19,829명을 정확히 골라내 원복할 수 있었던
> 유일한 이유가 이 키였다. 없으면 되돌릴 방법이 없다.

**■ 멈춤점 5** — 여기서 반드시 멈춘다. 관리자 화면을 열어 확인한다.

1. 상단 드롭다운에서 **815로또**를 고른다 → 방금 넣은 회원이 보이는가
2. 드롭다운에서 **플러스로또**를 고른다 → 기존 숫자가 그대로인가 (**여기가 8/31에 깨진 지점이다**)
3. 대시보드·매출에서 **플러스로또**를 골랐을 때 값이 3-2에 적어둔 기준값과 같은가
4. 넣은 회원의 등급이 맞는가 (실버·골드·다이아)
5. 조합 발송요일이 한 요일에 몰려 있지 않은가

하나라도 어긋나면 **전체 적재를 하지 않는다.** 아래 원복으로 되돌린다.

## 3-5. 전체 적재

```bash
python3 scripts/load-legacy-site.py \
  --site lotto815 \
  --archive ~/Downloads/815korean_paid_all_20260831.zip \
  --batch-id lotto815-20260908 \
  --apply
```

같은 배치 키를 쓴다. 이미 넣은 100명은 자동으로 건너뛴다.
2만 명 규모라 시간이 걸린다. 끝날 때까지 창을 닫지 않는다.

**■ 멈춤점 6** — 멈춤점 5의 확인을 다시 한 번 전부 한다.

## 3-6. 현장 확인 요청

# 문제가 생겼을 때

## 되돌리기

배치 키로 이번에 넣은 것만 정확히 지운다. **결제를 먼저, 회원을 나중에** 지운다
(순서가 바뀌면 참조 오류가 난다).

```sql
-- 1) 지우기 전에 반드시 건수부터 센다
select count(*) from payments where meta->>'import_batch' = 'lotto815-20260908';
select count(*) from members  where meta->>'import_batch' = 'lotto815-20260908';

-- 2) 건수가 예상과 맞을 때만 실행
begin;
delete from payments where meta->>'import_batch' = 'lotto815-20260908';
delete from members  where meta->>'import_batch' = 'lotto815-20260908';
-- 여기서 다시 세어 보고, 맞으면 commit / 이상하면 rollback
commit;
```

## 문자가 나갈까 걱정될 때

적재된 회원은 `meta.reco_paused = true`로 들어간다(로더가 자동으로 넣는다).
그래도 불안하면 **설정에서 전역 스위치를 내린다.**

- 설정 → 조합 자동발급 `weekly_free_reco.enabled` → 끔
- 설정 → 유료회원 조합문자 `paid_sms` → 끔

현장 검수가 끝나고 대표 승인을 받은 뒤에 다시 켠다(D178과 같은 절차).

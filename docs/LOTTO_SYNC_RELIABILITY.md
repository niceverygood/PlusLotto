# 회차 수집·당첨 집계 운영 절차

## 정상 처리
- 서버는 5분마다 인증 후 상태를 확인한다. 공식 결과를 검증해 새 회차와 작업을 원자적으로 등록한다.
- 회원/베팅 작업을 작은 배치로 처리한다. 배치 오류는 해당 배치 전체가 롤백되며 다음 실행에서 미완료 작업부터 재개한다. 완료 전에는 회차를 확정하지 않는다.
- 현재 회원 행을 잠근 뒤 당첨 이력만 수정한다. 대상과 해당 회차 첫 추천조합은 작업 등록 시점 스냅샷을 사용하고 원본 추천 이력은 보존한다.
- 기존 회차는 자동 재집계하지 않는다. 수동 집계 요청은 활성 관리자/실장만 가능하며 문자 없는 작업을 등록한다.

## 운영 화면
로또기록 상단에서 예상 최신 회차, 등록/집계 완료 회차, 최근 자동 점검, 처리 건수와 당첨회원 수를 확인한다. 다른 관리자 화면에서도 오류·지연 경고가 보인다. 상태는 1분마다 갱신되고, 15분 이상 자동 점검이 없으면 확인 필요로 표시한다.

표의 등수별 당첨은 베팅 집계다. 추천조합 당첨회원은 상단 집계와 이용자의 당첨회차 필터에서 확인한다. 적용 이전 회차에는 새 작업의 상세 통계가 없을 수 있다. 상세 통계를 채우기 위해 기존 회차를 자동 재실행하지 않는다.

## 실패 처리
- 공식 결과 미발표/형식 오류: 잘못된 회차를 저장하지 않는다. 공식 발표와 다음 점검 결과를 확인한다.
- 중단/시간 제한: 다음 실행이 진행 기록부터 재개한다. 새 작업을 중복 생성하거나 기존 회차를 삭제하지 않는다.
- 자료 오류로 blocked: 비공개 운영 경로에서 원본과 고정 오류 코드를 확인한다. 잘못된 원본을 수정했다면 관리자 수동 집계 요청으로 새 스냅샷을 접수한다. 수동 재집계는 문자를 보내지 않는다.
- 조회 실패/점검 지연: RPC 배포, 권한, DB 및 Vercel 실행 상태를 각각 확인한다. HTTP 200이나 배포 READY만으로 데이터 집계 완료로 판단하지 않는다.

## 문자 중복 방지
Plus의 기존 당첨문자 설정을 따르되, 발송 전에 DB outbox 선점과 회차 발송 표식을 기록한다. 선점 중 프로세스가 종료되거나 업체 응답을 받지 못한 경우 자동 재전송하지 않는다. 화면과 문자 기록의 접수확인필요 상태에서 확인하며, 일반 실패 문자 자동 재시도에서도 제외한다.

업체 접수 확인이 필요한 건은 회원·회차·시각을 업체 내역과 대조한 뒤 운영자가 처리한다. 확인 없이 outbox나 발송 표식을 삭제하거나 pending으로 되돌리지 않는다. 업체 접수와 휴대폰 실제 수신은 별도 증거다. 88은 이 자동 당첨문자 경로를 사용하지 않는다.

## 반영과 검증
1. 같은 마이그레이션을 서로 다른 두 프로젝트에 각각 적용한다. 스키마 적용은 기존 회차를 재집계하거나 문자를 생성하지 않는다.
2. 권한, 배치 롤백/재개, 동시 선점, 응답 유실, 기존 meta 보존 및 기존 회차 미재실행을 시험한다.
3. 운영 SHA·별칭, 인증된 무작업 점검, 읽기 전용 DB 결과를 대조한다. 기존 복구 영수증·집계·이관 보류 보존과 새 문자 요청이 없는지 확인한다.
4. 이관 보류, 실제 발송 승인, 사이트별 발신번호 및 현장 검수는 별도 전환 계획을 따른다.

## 되돌림
코드 복귀 전 미완료 작업과 선점된 문자를 확인하고 보존한다. 진행 중인 작업이 있는 상태에서 이전 순차 집계 코드를 바로 실행하지 않는다. 작업·outbox·발송 표식을 삭제하는 방식으로 복구하지 않는다. 변경 전후 값과 실제 대상을 확인한 별도 복구안을 작성한다.
